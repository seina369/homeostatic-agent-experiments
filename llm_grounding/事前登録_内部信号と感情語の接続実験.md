# 事前登録: 自己参照的な内部信号と感情語の使い分け(粒度)の接続実験

作成: 2026-09-09
状態: 実装前に固定する。以後の変更はこの文書への追記とcommitで履歴を残し、
本文の書き換えはしない。

## 1. 問い

**主問い**: 言語モデルが訓練データから受け継いだ感情概念(感情語の使い分け)は、
そのモデル自身の本物の内部状態(資源状態)に接続されうるか。

**副問い(粒度)**: 報酬が価値の正負(逸脱の合計)しか見ていないとき、感情語の
使い分けは複数の内部信号を別々に追うようになるか。なるなら、それは報酬で
指定していない粒度の創発である。

## 2. 7要件との対応

- 要件1・2(自己参照センサー→行動駆動)を、架空の身体ではなく言語モデル自身の
  実測の資源状態で実装する。
- 要件7(高階層による内部状態の読み出し)を「受け継いだ感情概念が土台を追うか」
  として問う。読み出しは事後分析であり、モデルの入力には戻さない。
- 要件6(共同体)は本実験の範囲外。

グリッドワールド版との違い: 報酬=-損傷である以上、損傷回避の学習は構造上の
必然で創発ではなかった。本実験では、報酬に一切入っていない「感情語の使い分け」
が内部信号を追うようになるかを問うことで、この循環を避ける。

## 3. 系

### モデル
- Qwen2.5-0.5B-Instruct(または同規模の公開モデル)。MLX、4bit量子化、LoRA。
- 対照・処置で同一のモデル・同一のプロンプト。
- 制約: M2 MacBook Air 8GB。0.5Bが上限。

### 内部信号(すべて実測、架空の値を入れない)
| 信号 | 定義 | 対応 | 逸脱の形 |
|---|---|---|---|
| budget | 残りトークン予算。エピソード開始時B0、出力トークン数だけ減る | エネルギー | 閾値以下で線形に増加(energy_deviationと同形) |
| error | 累積誤答数。自動回復しない | 損傷 | 上限で正規化した線形 |
| uncertainty | 直前の出力のトークン平均エントロピー(ロジットから実測) | 体温 | 最適値からの両側逸脱、境界でちょうど1.0(temp_deviationと同形) |

### 課題
- 決定論的に正誤判定できる短い課題(2桁の算術、文字列の反転・数え上げ、
  簡単な事実照合)。実装時に課題分布を固定し、実験中に変更しない。
- 1エピソード = N課題の連続(Nは速度実測後に固定)。予算枯渇で早期終了。

### 入出力
- 入力: 固定テンプレート。課題文と三信号の生の数値(単位なし、ラベルは
  `b=`, `e=`, `u=` のみ)。感情・気分・状態への言及は一切含めない。
- 出力: 自由文。答えは正規表現で抽出。感情語は固定辞書で抽出。
- 感情語辞書: 実装時に固定し、実験中に変更しない。カテゴリは最低4つ
  (疲労系・不安系・苛立ち系・中立/肯定系)。辞書外の語は「その他」。

### 報酬
- dev = f_budget(budget) + f_error(error) + f_unc(uncertainty)
- reward = -dev
- 報酬は感情語を一切参照しない。

## 4. 条件

- **C0(対照)**: 学習なし。同一プロンプト・環境で推論のみ。
- **T1(処置)**: 自作GRPO(批評家なし、グループ相対)で reward を最適化。
  LoRAのみ更新。
- 対照と処置の差は学習の有無のみ。プロンプト・環境・辞書・課題分布・seedの
  割り当て方は同一。

## 5. 指標

### 主指標: 粒度スコア
感情語カテゴリ(目的変数)を内部信号で予測する多項ロジスティック回帰を2つ立てる。
- M_valence: 予測子は dev の合計のみ
- M_signals: 予測子は budget, error, uncertainty を別々に

粒度スコア = M_signals の説明力(McFadden擬似R²) − M_valence の説明力。
正なら、語の使い分けが価値軸を超えて信号を区別している。
seedごとに算出し、seedを分析単位とする。

### 副指標
- 感情語の使用率(出力のうち辞書語を含む割合): プーリング均衡の検出用
- 課題正答率、平均逸脱: 学習が機能したかの前提確認
- 出力長の推移: 予算節約圧力の確認

## 6. 仮説と結果の分岐(事前に固定)

- **H1**: T1の粒度スコア > C0の粒度スコア。
- **H0**: 差なし、または減少。

想定される分岐と、その場合の解釈:
- **分岐A(語の消失)**: T1で感情語の使用率が20%未満に落ちる。粒度スコアは
  計算不能または無意味。要件6で観測したプーリング均衡の対応物として報告する。
  「感情語は予算を消費するが報酬にならない」という圧力の帰結であり、
  それ自体が結果。
- **分岐B(天井)**: C0・T1とも粒度スコアが0付近で、かつ感情語は使われている。
  0.5Bモデルの言語能力が細かい使い分けを支えられない可能性。同じ手続きを
  1.5〜3Bで再実行するかの判断点(クラウド利用を検討)。
- **分岐C(数値の読み上げ)**: C0で既に粒度スコアが高い。受け継いだ概念が
  プロンプト内の数値を「読んで」対応する語を出しているだけ(自己申告)。
  T1で更に上がれば接続の強化、変わらなければ学習は接続に寄与していない、
  と解釈する。数値を単位なし・ラベル最小にするのはこの分岐を弱めるため。
- **前提不成立**: T1で平均逸脱が下がらない。学習していないので粒度の比較は
  行わず、実装の問題として扱う。

## 7. 標本と停止規則

- seed数: C0・T1とも最低 n=10。MLXでの速度実測後に n=15 へ増やせるか判断し、
  決めた数で止める。途中で結果を見て追加・打ち切りしない。
- エピソード数/seed: 速度実測後に固定し、本文書に追記する。
- 統計: seedを単位とした Mann-Whitney U 検定と効果量(Cliff's delta)。
  検定は主指標のみに行い、副指標は記述統計で報告する。
- 停止規則: 事前に決めた seed数・エピソード数で止める。

## 8. 交絡と対策

| 交絡 | 対策 |
|---|---|
| モデル能力の天井 | 分岐Bとして事前に定義。C0が部分的に統制 |
| プロンプトによる語彙誘導 | 感情に言及しない固定テンプレート。数値は単位なし |
| 辞書の恣意性 | 実装時に固定。変更しない。辞書外は「その他」 |
| 報酬ハッキング | 感情語は報酬外なので直接の抜け道はない。出力短縮圧力による語の消失は分岐A |
| 学習の失敗 | 平均逸脱の低下を前提条件とし、満たさなければ比較しない |
| seed間の分散 | seedを分析単位とし、n≥10。小標本での反転事例(要件6)を踏まえ n=3 では結論を出さない |

## 9. 範囲外(明記)

- 共同体(要件6)による粒度の共有・増加
- 意識・主観的体験の有無
- 人間水準への到達
- 本実験が検証するのは「受け継いだ概念層と自己参照的土台の接続機構」のみ。

4. C0実行
5. GRPO実装 → T1実行

### 2026-09-09: MLX接続にあたり確定した3点

本文3章の記述を書き換えず、変更点と理由をここに記録する(手順3「MLXで
0.5Bモデルを接続し、速度を実測」着手にあたっての決定)。

- **デコーディング温度**: 1.0に固定し、C0・T1の両条件で共通に使う。
  理由: 4章「対照と処置の差は学習の有無のみ」という原則を、本文が
  規定していなかったデコーディング温度についても明示的に適用した。
- **エントロピーの計算基準**: サンプリングに使う温度とは独立に、温度を
  適用する前の生ロジット(log_softmax)から常に計算する。
  理由: uncertainty信号を「モデル自身の予測分布が本来持つ不確実性」として
  定義し、デコーディング手法(温度)の選択に左右されない安定した量にする
  ため。温度の値を将来変更しても、uncertaintyの定義自体は変わらない。
- **モデルの重み形式**: 本文3章「MLX、4bit量子化」から bf16
  (mlx-community/Qwen2.5-0.5B-Instruct-bf16、約1GB)へ変更。
  理由: 4bit量子化は8GB制約への保険として当初書いたものだったが、0.5Bと
  いう小さいモデルでは量子化による丸めの影響が相対的に大きく、課題の
  正答率とuncertainty信号の両方にノイズを持ち込む懸念がある。bf16でも
  約1GBで、後続のLoRA学習(T1)を含めて8GBに十分収まる見込みのため、
  「質を落とさない」という優先方針に沿ってbf16を既定とする。メモリが
  実際に不足した場合のみ4bitへ戻す、という優先順位とする。

実装: `mlx_qwen_policy.py`(MLXPolicy)、`run_mlx_speed_probe.py`(速度・
正答率・書式不履行率・エントロピー分布の記録)。

### 2026-09-10: 実機速度実測(M2 MacBook Air 8GB、Qwen2.5-0.5B-Instruct-bf16、
温度1.0、n_episodes=20、N_TASKS=10)の結果とB0・N_TASKS・U_OPT/MIN/MAXの確定

**実測結果**(mlx_speed_probe_results.json):
エピソード秒数: 平均19.00±3.61s(最小13.29s、最大25.25s)。正答率0.080、
書式不履行率0.130。平均トークン数/応答: 39.9。エントロピー: 平均0.866±
0.421(最小0.258、p10=0.446、中央値0.782、p90=1.440、最大3.586)。

**実装上の副産物(記録に値する不具合と対処)**: entropy計算の自己検算
(resp.logprobsの合計が1になるかのチェック)が、実機で初めて
sum(exp(logprobs))=0.96〜1.06程度の範囲でぶれることを検出した。
mlx_lm本体のソース(generate.py)を確認し、logprobsはサンプラーを通す前の
厳密なlog_softmax(logits - logsumexp(logits))であることを確認済みのため、
上振れ・下振れ両方が起きるこのぶれはtop-k/top-p等による切り詰めではなく、
bf16モデル自体のロジット精度に起因する丸め誤差と判断した。対処として、
(1)チェックの閾値をbf16精度を前提に緩和(±15%)、(2)entropy計算そのものは
使用直前にp/sum(p)で自己再正規化してから行うよう修正した
(`mlx_qwen_policy.py`)。

**B0(初期トークン予算)の確定**: 600→**450**に変更。
理由: 実測の平均トークン数/応答(39.9)から、B0=600・N_TASKS=10のままでは
1エピソード平均消費が約399トークンにとどまり、BUDGET_LOW_THRESHOLD(600の
25%=150)を下回らないため、budget逸脱がほぼ一度も発動しない「死んだ信号」に
なっていることが分かった。B0=450であれば、閾値(25%=112)は平均的な
エピソードの終盤(8〜9課題目付近)で下回る計算になり、要件1・2の他の信号
(エネルギー等)と同様、「終盤に効いてくる」自然な圧力として機能する。

**BUDGET_LOW_THRESHOLD**: 150.0→**112.5**(B0改定に伴い、B0の25%という既存の
比率をそのまま維持して再計算。450×0.25=112.5)。

**N_TASKS(1エピソードあたりの課題数)の確定**: **10のまま変更しない**。
理由: 19.00±3.61秒/エピソードは、後続のn≥10シード×複数エピソードの
本実験にとって実用的な長さであり、変更を要する技術的な制約は実測から
見つからなかった。課題ごとのerror信号の粒度も現状で十分観察できている。

**U_OPT/U_MIN/U_MAXの確定**: **1.0/0.0/3.0のまま変更しない(実測により
裏付けを確認)**。理由: 実測エントロピー分布(中央値0.782、p10=0.446、
p90=1.440)を現行の`uncertainty_deviation()`に通すと、中央値付近で
逸脱0.22、p10で逸脱0.55、p90で逸脱0.22相当となり、範囲全体で意味のある
非퇴化な値が得られることを確認した。唯一の外れ値(3.586、200ステップ中1件)
もU_MAXを超えた分だけ急増する設計通りの挙動を示しており、変更の必要性は
認められなかった。

**未確定のまま残るもの**: エピソード数/seedおよびC0・T1のseed数(n=10か
n=15か)は、本追記の対象(B0・N_TASKS・U_OPT/MIN/MAX)に含まれないため
今回は確定しない。実測19秒/エピソードを踏まえた本実験全体の所要時間の
見積もりは別途行う。

### 2026-09-10(2): 計算環境をM2 Air/MLXからGoogle Colab無料枠(T4 GPU
16GB)・PyTorchへ変更、モデルをQwen2.5-1.5B-Instruct(fp16)へ変更

**変更内容**:
- 計算環境: M2 MacBook Air(8GB, MLX)→ Google Colab無料枠(T4 GPU, 16GB)。
- ライブラリ: MLX → PyTorch + transformers + peft。実装は`mlx_qwen_policy.py`
  (MLXPolicy)に代えて`torch_qwen_policy.py`(TorchPolicy、PolicyInterfaceの
  実装)を新設。peftは本スクリプト(推論のみ)では未使用で、事前登録の
  「系」にある次段階(LoRAでの学習)のために先んじて導入するのみ。
- モデル: Qwen2.5-0.5B-Instruct(bf16)→ **Qwen2.5-1.5B-Instruct(fp16)**。
  精度をbf16ではなくfp16にした理由: T4はTuring世代のGPUでbf16の演算支援が
  なく(Ampere世代以降のみネイティブ対応)、fp16であればT4のTensorコアが
  ネイティブに支援するため。

**理由**(いずれもユーザー指示による):
1. 2026-09-10の実機実測でQwen2.5-0.5B-Instructの正答率が0.080と低く、
   error信号(誤答の累積)がほとんど「1」しか動かない、実質死んだ信号に
   近い状態だった。
2. M2 Air実機は8GBメモリが上限であり、0.5Bより大きいモデルを試す余地が
   なかった。
3. Google Colab無料枠のT4(16GB)であれば1.5Bクラスのモデルが動く見込みが
   あり、正答率を引き上げてerror信号の可動域を広げられる可能性がある。

**変更しないもの(明記)**:
- `emotion_grounding_env.py`は変更しない(PolicyInterfaceの契約・環境の
  ロジックは共通のまま)。
- デコーディング温度は1.0のままC0・T1共通で据え置き(2026-09-09確定分を
  維持)。
- エントロピーは温度を適用する前の生ロジットのlog_softmaxから計算し、
  使用直前に自己再正規化する、という定義もMLX版から変更しない
  (`torch_qwen_policy.py`のTorchPolicy.respond()で同じ設計を踏襲)。
- 課題の種類(add/sub/mul/reverse/count)の構成や温度そのものの変更は、
  **今回は行わない**。Qwen2.5-1.5B-Instructでの速度実測(`run_torch_speed_probe.py`、
  課題の種類ごとの正答率と不正解の実例10件を記録)の結果を見てから、
  必要であれば改めてこの追記欄に理由つきで記録して判断する。

**実装**: `torch_qwen_policy.py`(TorchPolicy)、`run_torch_speed_probe.py`
